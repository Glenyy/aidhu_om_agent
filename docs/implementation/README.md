## 2. 阶段内的执行流程

~~~mermaid
flowchart TD
    A[进入阶段前：检查上一阶段与当前文件] --> B[逐项讨论本阶段小步骤]
    B --> C[保存具体方案与待决事项]
    C --> D{用户审阅批准覆盖步骤}
    D -->|修改意见| B
    D -->|批准| E[按批准范围开发并验证]
    E --> F[阶段自动化审阅：工具检查与代码核对]
    F --> G{审阅通过}
    G -->|失败| H[修复批准范围内问题并复审]
    H --> F
    G -->|通过| I[生成实际手动操作审阅指南]
    I --> J[用户操作与结果反馈]
    J --> K{用户接受阶段结果}
    K -->|问题反馈| H
    K -->|接受| L[进入下一阶段的开发前讨论]
~~~

自动化审阅通过表示工程检查及阶段条件有对应证据，不表示人工已验收。阶段完成报告先标为“待手动审阅”；用户接受后才更新为“阶段已接受”。

## 3. 开发前讨论与批准

进入阶段时执行：

1. 阅读阶段文档、相关 plan、当前代码与上一阶段报告，列出与初始拆分的差异。
2. 对拟执行的小步骤补充具体改动文件、接口/数据、配置、验证方式、完成条件及需用户决定的事项。
3. **将定稿的小步骤直接写入 stages/<阶段ID>-*.md 阶段文档**，并在文档内记录决定、验证方式、完成条件与审批记录。用户 2026-10-06 决定不再新建独立的 preparations 开发前方案文档；`preparations/` 与 [开发前方案模板](templates/开发前方案模板.md) 自该日起停用，仅保留作历史参考。
4. 交由用户审阅；保存批准版本、明确覆盖的步骤 ID、约束及批准原话/日期。
5. 只有获批范围内的步骤可以进入实现。可以一次批准同阶段多个已讨论步骤，无须对覆盖范围内的常规动作重复请求批准。

初步路线图、目录审阅、泛指“进入下一步”或文档生成，不自动表示所有后续实现已批准。若用户明确针对已讨论方案授权开发，按该授权记录并执行。

实际开发发现需要改标签规则、接口语义、依赖方案、数据用途或已批范围时，先更新具体方案并取得对应审阅。批准范围内为达到完成条件的修复可以继续处理，不重复申请相同授权。

## 4. 每阶段结束的自动化审阅

每个阶段开发完成后，当次工作中自动执行审阅，不依赖定时任务、GitHub CI、额外子代理或用户另行催促。

审阅至少包括：

- 核对批准步骤、实际改动文件、阶段条件，检查遗漏与超范围变更。
- 执行已实现且适用于本阶段的测试、类型检查、构建或数据完整性检查，保存命令、环境、退出结果和证据位置。
- 静态核对核心代码与前后阶段合同：三分类、输入范围、阶段一隔离 a、原 ref、预算、事务及恢复等，只检查当前已实现的部分。
- 复验已有关键行为，尤其检查与本阶段有关的回归；不要对无关低影响文档/样式重复增加镜像测试。
- 核对敏感配置、输入/编号/原预测及阶段产物的处理符合约定。
- 失败时记录原因，在批准范围内修复，重跑受影响项，更新报告。

模型输出的格式通过不等于业务判断正确。模拟检查、实际模型兼容和人工标准下的分类质量分别记录；未执行项不得写为通过。真实服务调用沿用已批准样例与用量范围，避免不必要重复。

报告采用 [自动化审阅模板](templates/自动化审阅报告模板.md)。同轮报告完成后有影响结论的代码变更，应更新证据并复审。

## 5. 手动操作审阅文档

自动化审阅通过后，在同次阶段交付中生成 reviews/manual/<阶段ID>/r01-手动操作审阅.md，使用 [手动指南模板](templates/手动操作审阅模板.md)。

指南必须根据实际实现填写：

- 环境、代码/配置版本、准备数据及准确位置。
- 可复制的真实命令，或明确的页面点击顺序。
- 每步应看到的输出、文件、计数、状态和失败提示。
- 至少一个本阶段核心成功流程，以及已批准的必要异常/边界场景。
- 结果记录表、失败复现资料、恢复/停止说明。

只有实际可用的操作才能出现在交付指南中，不能拿当前占位脚本或未来命令假装已可运行。前端尚未开发的阶段可使用实际 CLI、Python 小型验证入口或文件/数据库查看步骤，不要求提前实现网页。

用户结果写入 reviews/manual/<阶段ID>/r01-用户审阅结果.md 或由开发者根据用户明确反馈记录，注明来源。没有反馈时为“待用户操作”，不能代填通过。

## 7. 状态与进入条件

阶段状态依次为：待讨论 → 待用户批准 → 已批准 → 开发中 → 自动化审阅中 → 待手动审阅 → 阶段已接受。出现检查失败或用户问题时为“需返工”，保留原状态历史。

下一阶段业务开发需要上一阶段已接受，且自身小步骤已按方案获批；提前准备讨论材料不等于开始实现。用户后续明确调整范围或顺序时，记录新决定并更新受影响阶段，不忽略其最新授权。

总体业务、技术与质量基线仍见 [规划入口](../../plan/README.md)。开发流程规则见 [阶段执行规则](../../.claude/rules/development-workflow.md) 与 [审阅交付规则](../../.claude/rules/review-and-handoff.md)。
