## 3. 代码与合同核对

- **业务三类与计分口径**：`metrics.py` 的混淆矩阵行＝人工真值、列＝agent 预测；逐类 TP/FP/FN/精确率/召回率/F1；Macro-F1 为三个 F1 的**算术平均**（不按条数加权，代码与报告文字一致）；计分只读 `records.final_label`（agent 原预测），`review_required` 参与评分不剔除。
- **零分母与「不可计算」**：`MetricValue.computable=False` 时 `display` 记「不可计算」，`_checks_passed` 要求**全部** `passed is True`，因此「算不出来」不算通过（已由演示数据的 4/4 未达标与 `test_evaluation_metrics.py` 双向覆盖）。
- **技术失败与漏评不进矩阵**：`FF-1` 无预测 → 计入 `missing_ids`／`failed_ids`、拉低分类完成率（19/20），**不出现在矩阵内**（矩阵和 19）。这与 plan/04 §6 的第三道门槛一致。
- **三道闸门顺序**：编号集合同构（`ID_SET_MISMATCH`）→ gold 校验（`GOLD_INVALID`）→ gold 摘要与清单一致（`GOLD_MISMATCH`）；三者均在实跑中真实触发（§2.2）。**它们是「划分不得混用」的技术保证**，但**不保证「保留集没被跑过」**——那一条是流程承诺，本轮以「只上传校准子集」遵守。
- **迁移与备份**：`SCHEMA_VERSION 2 → 3`，追加 `003_evaluations.sql`；新增测试真实构造 v2 库、跑真实迁移、断言 `applied_now == (3,)`、**迁移前备份文件存在**、旧数据（run 行）保留、三处 `IntegrityError` 约束生效。既有 `test_v2_migration_upgrades_an_existing_v1_database` 仍只验证 001→002，两条各管一段。
