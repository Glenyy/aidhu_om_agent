## 3. 代码与合同核对

### 3.1 记录查询（S06-01，plan/08 §6 逐条）

- **列表**：固定 `order_index` 升序，返回筛选后 `total` 与批次 `revision`；键集与 §2 命令 7 完全一致，**不含 `a` 与任何 ref**（plan/08 §6「列表不传 a 和全部 ref」）。
- **筛选**：多项 AND；`label`／`status`／`review_required`／`record_id` 各有用例（`test_record_list_filters_*`）；非法枚举与越界分页返回 422 且**不回显收到的值**（信封只给字段位置与提示）。
- **输入失败与技术失败分开**：`failure` 只放 `failed` 行的 `failure_json`，输入失败行不进 `failure`（`status` 已是 `input_invalid`），原因在详情的新增只读字段 `input_error` 里；`test_record_list_distinguishes_input_invalid_from_failed` 守住。
- **详情**：`input` 用**建批次时的快照**（`raw_input_json`，13 列原文）而非按当前模型重拼；`stage1`／`stage2` 直接回库里的原文（阶段二 `stage1_corrections` 不被重排压平）；`attempt_summary` 沿用 `agent/pipeline.py::result_to_payload()` 的现成形状。
- **`record_key` 语义**：记录接口的路径参数是**内部 UUID**（`records.record_key`），不是预检响应里那个可读键（§1.1 第 ④ 项）。记录存在但不属于该批次时返回 404（不区分「不存在」与「不在本批次」），避免漏出别的批次的存在性。

### 3.2 上传防护、错误合同与任务读库（S06-02）

- **三项防护**位于 [excel/reader.py](../../../../../src/aidhu_om_agent/excel/reader.py)：`MAX_EXPANDED_RATIO = 8`（解压总量 = `8 × limits.max_upload_bytes`）、`MAX_SHEET_CELLS = 500_000`、`MAX_VISIBLE_SHEETS = 50`；解压总量与可见表数在**打开工作簿之前**用 `zipfile` 读成员 `file_size` 求和判定（不解压）。
- **超限行为**：422 `BAD_WORKBOOK`，文案给出**实际值与上限**；**不裁剪资料**（直接拒绝，不改写工作簿）；被拒的上传**不留文件**（`test_expanded_size_rejection_leaves_no_file`、`test_sheet_count_rejection_leaves_no_file`）。`413 FILE_TOO_LARGE` 仍只用于压缩包字节数（`test_compressed_size_still_reports_413_alone`），两个量级可由不同文件分别触发（`test_both_scales_can_be_hit_by_different_files`）。

### 3.3 批次收尾与 `last_error` 语义分工（S06-03）

- `worker._finalize` 对 `partial_failed` **写 `last_error = None`**，收尾摘要由 `failure_summary`（`count`／`items`／`truncated`）与 `counts` 承载；`_fail_systemically` 路径**照旧写**（并有暂停派发标志）。**两条用例都验实际形状**：新批次 `last_error is None`、`model_dispatch_paused is False`；存量形状 `{code: PARTIAL_FAILED, failed_count}` 由 `test_run_detail_still_renders_legacy_last_error` 直接写回库、断言读口**原样返回**（新代码不迁移、不改写旧数据）。
- 界面横幅按上表 ③ 改为条件显示，且补上此前模板未渲染的失败数；`partial_failed` 页面上不再出现红色错误横幅，改为收尾摘要 + 一键跳到筛好的失败列表。

### 3.4 记录界面（S06-04）

- 批次详情页记录区块：序号／编号（空显示「（无编号）」）／来源行／q 摘要／状态／标签／需复核／失败码，另加固定「详情」列；失败摘要表的同一列同步。**序号列按 §2.1 第 1 项显示 `order_index + 1`（人读序号，与导出 1..N 一致）**，并在表下与记录详情页写明存储层的 `order_index` 从 0 起、两者差 1——本轮最后一步把原先直接显示 `order_index` 的列改成 `+1`，属与已批准界面清单对齐（非新增范围）。

### 3.5 首页改造（S06-05）与两种运行方式（S06-06）

- 首页只剩「上传 → 预检 → 开始判别（整批）」；模式是**只读指示**，取值来自**最近一个批次**的详情（`execution_control.last_worker` 是全局 `runtime_state`，任一批次都报同一个 worker）与 `call_statistics.*.simulated` 之和；没有任何批次时明确显示「还没有任何批次」，不猜。没有 worker 时给出提示：批次会**排队**，但不会有记录被判别——**排队不是失败**。
- 数据来源不新增接口（S06-05 的批准文件清单不含后端）：`fetchRuns(1, 1, null)` → 最新批次 → `fetchRun` → 取 `last_worker` 与调用统计；取不到时显示 `未知` 并把错误码与消息原样显示（形如 `[code] message`），不兜底吞掉。
- 构建产物模式：SPA 回落对所有方法登记、`/api/...` 一律 404 信封（见 §4 问题 1），静态文件仍**只对 GET/HEAD** 按文件返回，写请求给 405 信封；目录穿越由 `candidate.is_relative_to(root)` 挡住。
- dev 模式：vite 代理 `/api → 127.0.0.1:8000`，页面由 vite 提供，接口照常 404 信封（不挂回落）。
