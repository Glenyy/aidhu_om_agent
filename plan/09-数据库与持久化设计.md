# 09 数据库与持久化设计

规划版本：v2.3｜日期：2026-10-05｜状态：待用户审阅

首版使用本地 data/state.sqlite3，普通 sqlite3 接口，不引入 ORM。以下为逻辑表、字段和事务设计，不是已执行的建表脚本。配套[API 合同](08-API接口与数据合同.md)与[状态恢复](10-任务状态与恢复设计.md)。

## 1. 保存原则

- 原 Excel 文件保持不变；批次同时保存解析后的 13 个输入字段。后续分类、恢复和导出使用该批次快照。
- record_id 保存业务编号文本，不改成内部流水号；record_key 作为内部主键，缺编号失败行仍可追踪。
- 解析中的编号转换规则版本化；保留原单元格值供追踪，文本编号的前导零不丢失。具体输入格式兼容用样例验证。
- 已通过校验的阶段结果不可修改。R1 的更正保存在阶段二，不能覆盖 V3 原结果。
- 失败、调用次数、版本和人工复核标记与业务标签分开。
- 快照包含非敏感配置、两份提示词完整内容及摘要、规则/结构/解析版本；不保存密钥、请求头或模型推理链。
- 不自动复用其他批次的模型结果，不自动删除数据，不在数据库保存人工修订标签。
- JSON 字段用 TEXT 保存，写入前由程序校验；首版不依赖 SQLite JSON 扩展。

## 3. 输入、批次与记录

| 表 | 字段与职责 | 约束 |
| --- | --- | --- |
| uploads | upload_id；original_filename、relative_path、sha256、size_bytes、sheets_json、created_at | 路径由后端生成且唯一；文件完成写入才登记 |
| input_validations | validation_id；upload_id、sheet_name、status、file_sha256、input_contract_version、counts_json、report_json、created_at | status 为 passed/blocked；原预检不覆盖 |
| runs | run_id；upload_id、validation_id、source_filename、sheet_name、input_digest、config_snapshot_json、prompt_snapshot_json、versions_json、status、revision、total_count、valid_count、input_invalid_count、skipped_blank_rows、last_error_json、created_at、started_at、finished_at | 只从 passed 预检创建；total_count = valid_count + input_invalid_count；valid_count ≥1 |
| records | record_key；run_id、record_id、source_row、order_index、q、a、refs_json、raw_input_json、input_error_json、status、final_label、review_required、failure_stage、failure_json、created_at、updated_at | UNIQUE(run_id, order_index) 与 UNIQUE(run_id, source_row)；同批次非空编号唯一 |

source_row 为工作表实际行号（从 1 开始，包含标题行位置）；order_index 为非空输入记录顺序（**从 0 开始**）。跳过全空行不重新编号，原 source_row 保留。空白编号的规范 record_id 为 null，原值仍在 raw_input_json 中，避免多条缺编号行因空字符串触发唯一约束。

> **2026-10-07 用户决定（起点定为 0，本行按实际合同更正）**：本行原写「order_index 为非空输入记录顺序（从 1 开始）」，与 S02 已实现并已验收的合同不一致——`excel/reader.py` 取 `order_index = len(records)`、`schemas/qa.py` 为 `Field(ge=0)`、S04 建表为 `CHECK (order_index >= 0)`、界面「顺序」列直接显示 `0`。用户确认**保持 0 起**，故更正本行，**不动已验收的 S02/S03/S04 代码，也不迁移存量数据**。面向上报或导出的人读序号（1..N）由**导出层单独生成**，不在存储层做 +1 平移。附带理由：`source_row` 已是 1 起且含标题行（第一条数据 `source_row = 2`），若 `order_index` 也改 1 起，两者恰好相差 1，容易被误读成 off-by-one；保持 0 起时两套编号一眼可分。

refs_json 固定包含 ref1—ref10。有效记录的值为资料文本，空资料使用空字符串；无法读取的失败行保留可读值和单元格位置，不伪造内容。q/a 只在输入失败行允许为空。

raw_input_json 只记录 13 个输入字段的原单元格值，不把额外“判断”列纳入模型输入或批次规范字段。完整原文件单独保留，这不是增加人工初标隔离步骤。

final_label、review_required 是校验后阶段二的查询投影，便于列表筛选；完整依据以 stage_results 为准。保存阶段二时同事务更新投影，恢复不改写 completed 记录。

数据库 CHECK 约束只允许三个合法标签，且非 completed 记录的 final_label/review_required 为 null。completed 必须有非空标签和 0/1 复核值；“已存在 stage2 结果”等跨表条件由阶段提交服务在事务内验证。

创建时 total_count、valid_count 等固定输入统计不变。classified、failed、review_required 等动态统计直接聚合 records，避免同时维护多份易失步计数。每次记录或批次可见状态更新递增 runs.revision。

## 4. 阶段、预算与调用

| 表 | 字段 | 约束与用途 |
| --- | --- | --- |
| stage_campaigns | campaign_id、record_key、stage、campaign_no、max_attempts、reason、created_by_job_id、created_at | UNIQUE(record_key, stage, campaign_no)；stage 为 1/2；max_attempts 首版为 3；reason 为 initial/explicit_retry |
| call_attempts | attempt_id、campaign_id、job_id、attempt_no、status、requested_model_id、returned_model_id、request_digest、final_content、usage_json、duration_ms、service_request_id、error_json、started_at、finished_at | UNIQUE(campaign_id, attempt_no)；attempt_no 为 1—3；running/succeeded/failed/unknown_after_interrupt |
| stage_results | stage_result_id、record_key、stage、attempt_id、result_json、schema_version、prompt_sha256、result_sha256、validated_at | UNIQUE(record_key, stage)，UNIQUE(attempt_id)；来源必须是同条同阶段的成功调用 |

每个阶段的首次执行有 campaign_no=1。重开预算新增下一轮 campaign，不删除旧行、不把旧次数清零。当前轮已用次数等于其 call_attempts 行数，包含结果未知的占位，不另存易失步的 used_count。

单条调用前先在短事务内检查预算并占用 attempt_no，再提交事务后请求模型。即使进程在发送前中断，已保留占位也计入预算；这是保守计数，不能凭“本地没收到答案”认定远端未调用。

格式、引用或业务一致性校验不通过也算一次失败调用。网络错误同样保留 attempt；服务的 reasoning_content 不保存，只保留最终响应内容与受控错误。service_request_id/用量没有返回时为 null。

阶段一成功时插入 stage_results，并将记录改为 stage1_done。阶段二成功时插入 stage_results，写入最终标签与复核投影，改为 completed。以上同时将 call_attempts 标为 succeeded，不能先标成功后遗漏阶段结果。

阶段二失败时 stage1 仍保留。未通过校验的候选不进入 stage_results，只留在 call_attempts 的最终响应和错误信息中。

只有明确允许的“重新尝试失败项”才新增 campaign；认证修正后仍有预算时继续旧 campaign。输入超限或永久参数问题需要新批次，不靠不断加 campaign 规避。

## 5. 任务、导出与幂等

| 表 | 字段 | 约束与职责 |
| --- | --- | --- |
| jobs | job_id、run_id、kind、mode、payload_json、status、worker_id、worker_slot、current_record_key、current_stage、result_json、error_json、created_at、started_at、last_activity_at、finished_at | kind 为 classify/export；一批次最多一个 queued/running 判别任务；worker_slot 仅 running 时为 1，其余 null，UNIQUE(worker_slot) |
| exports | export_id、job_id、run_id、source、scheduled_revision、captured_revision、captured_at、captured_run_status、captured_counts_json、created_at | job_id 唯一；source 为 automatic/manual；同 run_id/scheduled_revision 只自动安排一次 |
| artifacts | artifact_id、export_id、kind、relative_path、download_name、media_type、size_bytes、sha256、created_at | UNIQUE(export_id, kind)；kind 为 excel/jsonl；两份完整文件共同发布 |
| idempotency_keys | scope、key、request_sha256、http_status、response_data_json、run_id、job_id、created_at | PRIMARY KEY(scope, key)；scope 是方法与标准化路径；与操作同事务插入 |
| runtime_state | singleton_id=1、worker_id、worker_started_at、model_dispatch_paused、pause_reason_json、updated_at | 共享模型消费暂停信息；不代替操作系统独占锁 |
| schema_migrations | version、script_sha256、applied_at | version 主键；数据结构版本独立于规划版本 |

jobs 的 mode：判别为 initial/resume/retry_failed；导出为 automatic/manual。payload_json 保存选中的 record_key、计划使用/重开的预算及操作来源，不能放密钥。

last_activity_at 表示最近已保存活动，不是证明进程存活的心跳。R1 请求可能长达 300 秒，不能仅因时间戳未更新就抢占它。

系统性认证/配置故障同事务设置 runtime_state.model_dispatch_paused=1，保存脱敏原因；worker 此时仅消费导出任务。用户修正后重启 worker，验证配置并持有独占锁后更新 worker 标识、解除暂停；未修复的故障会再次触发暂停。该表不证明远程配置已修正。

自动导出在判别任务最终提交时入队；它是独立 export job，不要求用户创建第二次。导出失败不能改成 runs.failed。接口查询通过 jobs 与 artifacts 派生导出状态，不在多表重复维护同一任务状态。

exports.captured_* 在开始导出时固定。将所有已提交记录按同一读取快照载入内存，结束读事务后生成文件；过程中发生新的恢复入队不改变已经捕获的内容。

初始数据库结构版本拟定为 1；正式 DDL 与迁移脚本在开发时生成并验证。本稿没有执行建表。

## 6. 关键索引与一致性

部分唯一索引可约束特定子集，拟采用以下规则：[SQLite 部分索引文档](https://www.sqlite.org/partialindex.html)

~~~sql
CREATE UNIQUE INDEX uq_active_classification
ON jobs(run_id)
WHERE kind = 'classify' AND status IN ('queued', 'running');

CREATE UNIQUE INDEX uq_run_record_id
ON records(run_id, record_id)
WHERE record_id IS NOT NULL;

CREATE UNIQUE INDEX uq_automatic_export_revision
ON exports(run_id, scheduled_revision)
WHERE source = 'automatic';
~~~

以上是设计示意，完整表字段必须先按本文件创建。重复空编号以 record_key/source_row 追踪，不能把 null 编号互相当成重复。

常规查询索引建议：

- runs(created_at, run_id)：分页列表。
- records(run_id, order_index)、records(run_id, status)：顺序与状态。
- records(run_id, final_label, order_index)、records(run_id, review_required, order_index)：标签与复核筛选。
- jobs(status, created_at, job_id)：持久化队列。
- 各表外键及 stage_campaigns(record_key, stage, campaign_no)：关联和最新预算。

每次新建连接显式启用并验证 PRAGMA foreign_keys=ON；不能假定连接默认已开启。数据库还需检查外键一致性。[SQLite 外键文档](https://www.sqlite.org/foreignkeys.html)

SQLite JSON 文本结构和跨表业务条件由程序验证；唯一/CHECK/外键约束是另一层保障。阶段对应、计数和版本兼容不能仅靠有外键就认定正确。

## 7. 事务边界

| 操作 | 同一短事务内完成 | 事务外完成 |
| --- | --- | --- |
| 创建批次 | runs、全部 records、首个 classify job、幂等响应 | 读取配置/提示词、确认文件摘要、解析 Excel |
| 恢复入队 | 状态与预算检查、保存目标记录和计划、插入 job、run 变 queued、幂等响应 | 版本兼容检查准备；不调用模型 |
| 认领任务 | 检查独占槽、认领最早 queued、赋 worker_id、设置 running、必要时落实重开预算 | 执行流程与请求模型 |
| 保留调用 | 检查最新 campaign 次数、插入 running attempt、更新当前活动 | 模型调用与退避 |
| 保存阶段 | attempt 成功、stage_results、记录状态/投影、run revision | 解析与证据语义/位置校验 |
| 阶段失败/系统故障 | attempt 错误、记录失败信息、run/job 对应状态；系统故障设置消费暂停 | 等待与用户操作 |
| 判别结束 | run/job 终态、revision、自动 export job/exports | 文件生成 |
| 发布导出 | 两个 artifacts、export job completed、结果标识 | 生成临时文件、完成重命名、计算摘要 |

写事务采用显式 BEGIN IMMEDIATE 并及时提交/回滚。它仍可能因其他写入返回 BUSY，配置有限锁等待，业务操作不无限循环；API 返回可识别错误，worker 保留可恢复状态。[SQLite 事务文档](https://www.sqlite.org/lang_transaction.html)

Python 3.12 具有不同事务控制选项；实现需固定一种模式，避免隐式事务与显式 BEGIN 混用，并测试回滚及提交异常。不能依赖不同 Python 版本的默认行为。[Python sqlite3 文档](https://docs.python.org/3.12/library/sqlite3.html)

每个 API 操作和 worker 使用独立连接，不把连接对象跨进程共用。参数值使用 SQL 参数绑定，排序/列名从程序固定白名单选择。WAL、本地磁盘、busy_timeout 与短事务约定沿用详细设计。

## 8. 文件与数据库协同

SQLite 事务不能把磁盘文件写入也变成同一个原子事务，所以采用“文件完整后登记”的顺序：

1. 上传写临时文件，校验读取能力和摘要，重命名为唯一快照路径，再登记 uploads。
2. 导出写入 outputs/<run_id>/<export_id>/ 的临时文件，全部完成并关闭文件后重命名为最终文件。
3. 在一个事务内登记 Excel/JSONL artifacts，并将任务设为 completed。
4. 下载只访问已完成任务登记的文件；出现缺失或摘要不符时返回明确错误。

文件写好但数据库提交前中断可能留下未登记文件。首版保留并在恢复检查中记录，不自动删除，不把它当作可下载完成结果。再导出使用新的 export_id，不覆盖这些文件或人工已改文件。

运行路径都相对项目根目录解析并检查边界。文件路径不是 API 可写参数；原文件名不能决定输出目录。

## 9. 迁移、备份与验证

API/worker 启动先检查结构版本，迁移由启动流程在 worker 消费前串行执行。拒绝读取未来未知结构；旧版本需经明确迁移或使用兼容程序，不各进程同时执行 DDL。

迁移前停止消费并备份。运行中可通过 SQLite 备份接口获得一致副本，或停止全部数据库连接后备份；不只复制正在 WAL 模式写入的主文件。Python sqlite3 提供连接备份接口。[Python 备份接口](https://docs.python.org/3.12/library/sqlite3.html#sqlite3.Connection.backup)

开发验证包括：外键开启、唯一约束、预算保留、阶段提交回滚、API/worker 同时读写、文件写好但未登记、中断恢复、备份恢复及迁移版本拒绝。用模拟客户端验证 1000 条与最长资料组合，真实模型准确率另按质量规划验收。
