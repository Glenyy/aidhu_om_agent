# 10 任务状态与恢复设计

规划版本：v2.3｜日期：2026-10-05｜状态：待用户审阅

本文件统一批次、队列任务、记录和模型调用的状态，配套[API](08-API接口与数据合同.md)、[数据库](09-数据库与持久化设计.md)。状态机是拟定设计，尚未执行真实中断或模型测试。

## 1. 四种不同概念

| 对象 | 用途 | 状态或值 |
| --- | --- | --- |
| 批次 run | 这份 Excel 的整体处理情况 | queued、running、completed、partial_failed、failed、interrupted |
| 任务 job | 一次执行、恢复或导出操作 | queued、running、completed、partial_failed、failed、interrupted |
| 记录 record | 单条问答的已保存检查点 | pending、input_invalid、stage1_done、completed、failed |
| 业务判断 label | 已校验的最终三分类 | 回答正确 / 未检索到正确资料 / 检索到正确资料但回答错误 |

completed 标签结果仍可能需要人工复核。input_invalid、failed 或未完成记录的 label 为 null。需复核不属于失败状态，不增加第四类判断。

调用 attempt 另有 running、succeeded、failed、unknown_after_interrupt，用于计算预算和处理远端结果未知情况。它不能替代 record.status。

## 2. 批次状态与按钮

| run.status | 含义 | 页面主要操作 |
| --- | --- | --- |
| queued | 已保存、等待唯一 worker | 查看；不再创建恢复任务 |
| running | worker 正在判别 | 查看进度与已提交结果；不重复恢复 |
| completed | 所有有效行分类成功，且没有输入失败 | 查看、导出、下载已有文件 |
| partial_failed | 本轮可处理行已处理完，含输入或单条技术失败 | 查看失败；有可重试项时允许显式重试 |
| failed | 系统性错误阻止本轮继续，可能还有未处理行 | 查看原因；按修复类型恢复或新建 |
| interrupted | worker 被停止或退出，已保存检查点保留 | 符合版本和预算条件时恢复 |

批次 completed 不要求人工复核已经完成；它表示程序处理完成。partial_failed 不代表业务上两个错误标签，表示技术/输入失败。

导出独立显示 queued/running/completed/failed/interrupted。批次 completed 时导出可能仍排队，下载按钮需等待完整文件登记。

~~~mermaid
stateDiagram-v2
    [*] --> queued: 创建批次
    queued --> running: worker 认领
    running --> completed: 全部分类且无输入失败
    running --> partial_failed: 处理结束但有失败行
    running --> failed: 系统性故障
    running --> interrupted: 停止或异常退出后恢复检查
    interrupted --> queued: 显式恢复
    failed --> queued: 修复且允许沿用快照
    partial_failed --> queued: 有可重试项
    completed --> [*]
~~~

进入终态同时结束当轮 classify job；恢复新增 job，不将历史 job 从 interrupted/failed 改回 queued。created_at 不变，每轮 started_at/finished_at 与错误保存在 jobs；run 上只保留最近一轮及总体状态。

## 3. 记录处理与阶段提交

| 当前状态 | 条件与操作 | 下一状态 |
| --- | --- | --- |
| 输入读入 | 单条输入无效 | input_invalid，不调用模型 |
| pending | 阶段一校验成功并提交 | stage1_done |
| pending | 阶段一永久失败/预算耗尽/系统性停止 | failed，记录 failure_stage=stage1 |
| stage1_done | 阶段二校验成功并提交 | completed，保存 label 与复核标记 |
| stage1_done | 阶段二失败或系统性停止 | failed，保留阶段一结果 |
| failed | 有资格恢复，worker 开始执行且无阶段一结果 | pending |
| failed | 有资格恢复，worker 开始执行且已有阶段一结果 | stage1_done |
| completed | 任意普通恢复或导出 | 保持 completed，不重复调用 |
| input_invalid | 普通恢复或显式重试 | 保持 input_invalid；修正文件后新批次 |

阶段一资料不足或 uncertain 仍继续阶段二，没有从 V3 直接跳到业务标签的路径。

重试中的失败行在 worker 认领任务时才重置为检查点状态，不在用户点击恢复时提前擦掉错误。旧错误保留在 attempts/jobs；当前 failure 更新与预算落实同事务进行。

每阶段提交包含：成功 attempt、已校验 stage_result、记录状态和必要投影、批次 revision。不能出现“阶段一已保存但记录仍永久 pending”或“有最终标签但没有阶段二结果”的半次提交。

程序进入同批次恢复时先验证这些不变量。历史数据不一致应停止并报告，不通过猜测标签修复。

## 4. worker 生命周期

1. 验证配置、路径和数据库结构版本。
2. 获取操作系统级独占锁；锁失败就退出，不修改队列状态。PID 文件只是归属元信息，不能作为独占锁本身。
3. 持锁情况下检查上次遗留的 running 任务和调用，执行中断恢复登记；更新 runtime_state 的 worker 标识与启动时间，并在配置检查后解除上轮暂停。
4. 按 created_at、job_id 顺序认领 queued 任务，短事务设置 worker_slot=1。
5. 判别任务按输入顺序执行，每条阶段调用前保存尝试占位，返回后校验与提交。
6. 阶段失败按统一策略有限重试；不能在 SDK、worker 和 pipeline 各自再重试三次。
7. 判别结束更新 run/job、释放执行槽并安排自动导出；导出任务单独执行。
8. 无任务时短间隔检查队列；退出时释放锁，保留未消费 queued 任务。

重试执行职责固定为 agent.pipeline 中的阶段执行器；worker 负责调度，llm.client 只执行一次服务请求。默认两阶段各最多 3 次尝试，SDK 重试关闭。

网页关闭和 API 重启不会释放 worker 的独占锁，也不会取消它的模型请求。API 查询失败与 worker 退出是不同事件。

不根据 last_activity_at 超时抢占任务；长请求允许在配置超时内执行。只有新 worker 成功获得操作系统锁后才能把旧 running 标记为 interrupted。

## 5. 中断检查与恢复

| 中断位置 | 已提交内容 | 恢复行为 |
| --- | --- | --- |
| 上传/预检未登记 | 可能有临时或未登记文件 | 不存在可执行批次；用户重新操作，不误认为已创建 |
| 创建事务未提交 | 无完整批次和任务 | 同一幂等 key 重试创建；已提交时返回原 ID |
| classify job 入队但未认领 | queued 任务与输入快照 | worker 启动后自动消费 |
| 尝试占位前 | 原检查点 | 从该阶段开始，预算未占用 |
| 尝试占位后、远端结果提交前 | running attempt，远端情况未知 | 改为 unknown_after_interrupt，占用旧预算；有剩余次数才可继续 |
| 阶段一提交后 | stage1_done 和原分析 | 直接阶段二，保留全部原 ref |
| 阶段二提交后 | completed 和标签 | 跳过此记录 |
| 全部记录结束、批次终态未提交 | 所有记录终态，run/job 仍 running | 新 worker 标记 interrupted；显式恢复仅补终态和自动导出，不调用模型 |
| 判别终态与自动导出已提交 | run 终态、export job queued | worker 执行导出；不重新判别 |
| 导出文件已写好、登记前 | 未登记或未完整发布的文件 | 原导出标中断；新导出用新 export_id |
| 文件登记事务提交后 | 两个 artifacts、export job completed | 下载原文件，无需重复生成 |

启动恢复检查把旧 running attempt 改为 unknown_after_interrupt，旧 running job 改为 interrupted，清空 worker_slot。判别 job 对应 run 改为 interrupted；只有 export job 中断时不改变 run 的分类状态。

记录按已经提交的 stage_results 恢复检查点。若原阶段没有结果且最新预算已无剩余，设置 failed 并注明恢复需要重开预算。不会自动增加 attempt 数上限。

远端成功、保存前中断可能导致下一次请求再次调用。首版保证本地已提交检查点可复用，不承诺远端恰好一次或未知请求零费用。

## 6. 普通恢复与显式重试

所有操作首先检查：无活跃 classify job；输入与版本快照一致；原规则与结构可执行；原服务/模型配置可沿用。

### retry_failed=false：普通恢复

选中以下记录：

- pending 或 stage1_done，下一阶段尚未执行，或旧 campaign 仍有剩余次数。
- failed，但其故障可沿用原输入/配置处理，且对应 campaign 有剩余次数；例如修正环境凭据后继续。
- completed/input_invalid 不纳入。
- 预算耗尽的可重试行不重开，返回 skipped_budget_exhausted 数量。

如果旧 run 被中断但所有行已是终态，允许 finalize_only 恢复：selected_records=0，只计算 completed/partial_failed 并安排自动导出。它不是 NOTHING_TO_RESUME。

### retry_failed=true：显式重新尝试失败项

包含普通恢复可选记录，并对预算耗尽、可沿用原输入/配置的失败行计划开启新 campaign，最多 3 次。还未耗尽的 campaign 继续剩余次数，不为了“重试”直接重置成 3。

在入队事务保存目标 record_key 和重开计划，worker 认领时落实新 campaign。重复请求或中途再次恢复不会为同一计划再新增一轮。

### 不可在同批次修正的问题

| 情况 | 处理 |
| --- | --- |
| 输入缺失、编号错误、资料需修改 | 修改 Excel 后新建批次 |
| 上下文超限、输出截断需改限制 | 验证服务能力/配置，修改后新批次 |
| 模型、地址、关键参数配置错误 | 修正配置后新批次 |
| 原规则或结构不兼容 | 使用对应程序版本恢复，或新批次 |
| 人工希望重判一条 completed | 修改版本或输入后新批次，不覆盖既有结果 |

认证凭据轮换、原服务短暂不可用后恢复不改变非敏感快照，允许修正后继续。记录为相同模型 ID 不保证远程服务内部版本相同，该限制保留在报告中。

没有任何可选记录、也不需要 finalize_only 时返回 409 NOTHING_TO_RESUME。系统性错误要求改变快照时返回 409 CONFIG_CHANGE_REQUIRED；不能先跳过故障说明，继续用同一错误配置调用其余记录。

allowed_actions 包含后端计算的可选数、可重开数与禁用原因。前端不自行判断预算，提交时后端重新核查。

## 7. 重试和失败策略

| 错误 | 单阶段自动处理 | 对 run 的影响 |
| --- | --- | --- |
| 网络、超时、429、临时服务错误 | 默认最多 3 次，失败后等待 2 秒/4 秒 | 耗尽后单条失败，继续其他有效行 |
| 非法 JSON、标签、字段、伪造引文或矛盾输出 | 同一预算内反馈受控校验问题再试 | 耗尽后单条失败 |
| 认证错误 | 当前调用失败，不继续自动试满预算 | run.failed；修正凭据后按剩余预算恢复 |
| 模型/必要参数无效 | 当前调用失败，停止 | run.failed；按配置修正规则新建批次 |
| 上下文超限或输出截断 | 不裁剪资料、不反复碰运气 | 单条失败，需修正后新批次 |
| 数据库提交失败 | 停止消费并报告，不能宣称已提交 | 数据库恢复后按已提交状态检查 |
| 导出/文件写入失败 | export job.failed，保留分类结果 | 不改变分类 run 终态 |

自动重试不改提示词版本、资料内容或模型配置。修复反馈只包含本阶段受控校验错误，不能把 a 或阶段二历史带入阶段一。

认证/配置异常可能影响后续排队批次。首版在故障事务中设置 runtime_state.model_dispatch_paused，暂停新的模型判别任务并报告需要人工处理；导出任务仍可执行。暂停期间从队列选择最早导出任务，保留排队的判别任务。用户修正凭据/原服务后重新启动 worker；不能把尚未执行的其他批次自动标成错误。

正常有效记录两次模型请求；重试会增加调用数，用调用尝试记录统计，不把额外调用隐藏成正常两次。

## 8. 分类结束与导出

只有在本轮无未处理目标记录、无系统性阻断时，才按全部 records 汇总：

- 所有记录 completed：run.completed。
- 存在 input_invalid 或 failed，且其余行已经处理：run.partial_failed。
- 系统性错误阻止继续：run.failed，允许有 remaining。
- 进程停止：run.interrupted，允许记录进度达到 100%。

判别终态、当轮 job 终态、revision 和默认导出排队同事务完成。自动导出以 run_id + scheduled_revision 去重，不由页面轮询触发。

导出在认领时捕获同一数据库读取快照，记录 captured_at、captured_revision、批次状态和计数；全部载入后结束读事务再生成文件。仅有一份文件完成时不发布半组结果。

导出 completed 要求 Excel 和 JSONL 完整登记；任务错误不改写标签。中断/失败导出不通过 classify resume 重跑，用户使用新的 export 请求。

## 9. 页面交互与关键验证

| 状态/情况 | 页面行为 |
| --- | --- |
| 排队/运行 | 约每 2 秒查询；展示已处理、成功、失败与复核；恢复按钮禁用 |
| 任务终态 | 停止持续状态查询，显示总结；自动导出未结束则继续单独查询导出任务 |
| 网络断连 | 保留最后已确认状态并提示，有限恢复查询；不推断后台已停止 |
| 有可恢复记录 | 展示恢复按钮及选中/跳过数，不显示新预算已自动开启 |
| 预算耗尽可重试 | 明确“重新尝试失败项”，显示预计重开记录数 |
| finalize_only | 说明将补齐状态与导出，不再调用模型 |
| 有输入/超限问题 | 展示原因和来源行，提示新批次处理 |
| 需人工复核 | 保留暂定标签，提供资料详情和 Excel 下载，不在线覆盖预测 |

新增关键测试：占位后中断仍占预算、R1 中断复用 V3、预算耗尽显式续开、同一续开计划重复恢复、全部结果保存后 finalize_only、自动导出去重、认证错误不反复消费队列、导出半组文件不发布。

这些工程行为使用模拟客户端和真实多进程验证；真实服务的上下文、格式与分类质量按既有 M2/M5 要求独立验收。
