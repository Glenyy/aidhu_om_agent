### 建议开发顺序

先完成 M1 的目录与配置骨架，再打通 M2 的单条模型流程。在此基础上完成存储和 worker，随后开发 API 和前端，最后进行完整网页联调。前端展示可先用明确标注的模拟接口开发；真实任务和分类验收必须使用实际后端与模型服务。

目录方案见[项目目录与前后端选型](07-项目目录与前后端选型.md)。M0 尚未通过，此时只调整规划。页面交互、模型响应细节和提示词具体内容，在实际开发时结合情况设计并同步文档，不要求当前补齐新的专项规划。

## 3. 每项任务的完成定义

- 行为符合需求和详细设计，异常路径有明确状态。
- 涉及输入、引用、重试、持久化或指标的变更具有对应测试。
- 不新增第四种业务标签，不把技术失败映射成分类。
- 配置、日志与提交产物不含服务密钥。
- 用户可观察的行为已写入对应文档。
- 未完成、未验证或依赖用户核定的内容明确记录，不标为完成。

## 4. 阶段阻断与调整

| 情况 | 后续安排 |
| --- | --- |
| 尚未审阅通过 | 停留 M0，修改规划 |
| 模型服务不可用或无法完成最长样例 | 记录兼容问题，修正服务配置后重测，M2 不通过 |
| 人工标签或任一类别样本不足 | 补充核定数据，M4/M5 不宣称完成 |
| 校准结果较差 | 在校准集调整规则，记录原因，重新冻结版本 |
| 正式验收未达门槛 | 保留结果，分析误判；若用于调参，原验收集转回归集 |
| 修订改变需求或接口 | 更新相关规划并重新确认受影响内容 |

不为赶进度静默删 ref、缩小指标分母或把人工修订成绩算成 agent 成绩。

## 5. 职责与状态记录

用户负责业务口径、人工核定样本、规划和业务验收。开发者负责实现、工程验证、服务兼容报告与交付。

每个里程碑记录开始/结束时间、产物版本、已完成项、失败项和证据位置。日历安排在实际开发开始后，结合服务耗时、人员投入和核定进度估算。
