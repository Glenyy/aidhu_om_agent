# 阶段自动化审阅与手动交付规则

适用范围：整个项目，无路径限制。依据为 2026-10-05 用户要求：“每个阶段开发完成都需要自动化审阅一遍，然后给出一个手动操作的审阅步骤的md文档”；2026-10-06 用户补充：“手动验证只使用本项目的前端界面验证”。

关联：[阶段执行规则](development-workflow.md)、[实施入口](../../docs/implementation/README.md)。

## 1. 自动化审阅必须主动执行

每个阶段开发完成后，在当次工作中主动执行审阅，不等用户催促。不要求定时任务、额外子代理、GitHub 工作流或新线程；按实际工具与代码完成审阅。

自动化审阅不是只检查语法，也不是只让模型写一句“通过”。至少核对批准范围、实际代码与合同，执行适用的测试/类型检查/构建/数据检查，并验证受影响的关键回归。

使用 [报告模板](../../docs/implementation/templates/自动化审阅报告模板.md)，保存到 docs/implementation/reviews/automated/<阶段ID>/r01-自动化审阅.md。后续重要复审保存 r02 等轮次，注明针对的变更和前轮结论。

## 2. 记录真实证据

报告写明批准方案、代码/配置标识、日期、执行环境/目录、完整命令、退出码、关键结果和证据位置；关键代码核对注明文件或数据流。

分别报告：

- 工程模拟测试与实现完整性。
- 实际模型服务兼容性。
- 人工核定下的分类质量。

未执行不能记通过；工具或服务缺失不能直接改记“不适用”。真正不适用的检查说明原因。无 Git 时记录文件摘要或交付标识，不伪造提交号。

本阶段尚未实现的能力明确标为后续范围；不能要求用未来代码证明当前通过，也不能虚构已经验证。

沿用已批准的真实服务、样例和调用范围；已有证据充分时不重复付费验证。模拟 1000 条只证明工程行为，不证明真实模型准确率或性能。

## 3. 失败与复审

必需检查失败时，保留真实结果，在已批准范围内修复并重跑受影响检查。扩大范围按阶段执行规则更新具体方案。

检查未完成或仍有影响完成条件的问题时，不能宣称阶段通过。正式保留集用于调试后转为回归集，新的质量验收使用未参与调试的数据。

审阅后代码变化影响结论时，更新证据、版本和指南并复审；保持结论与交付版本一致。

## 4. 手动审阅默认经前端界面（用户 2026-10-06 决定）

用户要求：手动验证**只使用本项目的前端界面**，不再以终端命令作为验收路径。因此：

1. **每个需用户手动验收的阶段必须交付可用的界面验证面。** 阶段划分与批准的步骤中必须写明该阶段的界面增量；没有界面的阶段不能作为用户验收路径交付。这与阶段执行规则 §2 的讨论要求绑定，在批准步骤时一并确认。
2. **界面必须能用真实数据走通该阶段的核心成功流程和必要异常/边界**，不能只有静态占位页或"未来按钮"。界面验证面至少能：导入/选择输入、触发该阶段动作、看到可核对的结果。
3. **涉及真实模型的步骤，界面必须提供模拟模式。** 手动验证默认走模拟，用于验证交互、流程与边界；真实调用单独授权、限制在少量样例，并在界面上和指南中都明确标注会产生真实调用与费用。**不得在手动复验中静默调用大批量真实模型。** 模拟模式的界面必须有明显标识，防止模拟结果被当成真实结果。
4. **界面覆盖不到的产物必须显式说明，并给出界面内可核对的替代方式**，例如导出文件可下载后打开、worker 行为可在界面上看到状态变化。不能因为"看不了"就默默略过；确属无法界面化的检查（如命令行契约、数据文件内部结构），在指南中单独列出并说明为什么，同时给出可核对的证据位置。
5. **界面验证同样要留下可核对值**：编号、计数、状态、文件名、前后对比（如原文件 hash）。只写"界面显示正常"不算通过证据，也不得由开发者代填。

## 5. 同次阶段交付必须附手动操作 Markdown

自动化审阅通过后，立即根据真实实现生成 docs/implementation/reviews/manual/<阶段ID>/r01-手动操作审阅.md，使用 [手动操作审阅模板](../../docs/implementation/templates/手动操作审阅模板.md)。

指南必须包含：

- 适用版本、自动化报告链接、环境、项目路径和准备数据。
- **实际页面点击顺序**（默认形式）：从启动服务到看到预期结果的每一步，含界面地址与必要的前置启动命令。
- 每步可核对的页面元素、输出、编号、计数、状态及预期错误。
- 阶段核心成功流程和必要异常/边界操作。
- 用户结果填写表、反馈要求、停止/恢复及文件保存说明。

CLI 或 Python 入口只能作为补充与排错手段，或在规则 §6 允许的过渡期使用。不能用当前占位脚本、未来按钮或未经验证命令交付。模拟/真实模式明确注明，不在手动复验中静默调用大批量真实模型。

界面尚未覆盖某项已实现能力时，指南必须说明该项的核对方式，并在后续阶段补齐界面后提供复验步骤。

## 6. 界面就绪前的过渡期

前端界面要到 S03 才随该阶段一并交付（用户 2026-10-06 决定，见 [S03 阶段文档](../../docs/implementation/stages/S03-模型适配与两阶段判别.md)）。在此之前已实现但未验收的阶段：

- 已生成的 CLI 版手动指南**保持原文不改写**，仅作为历史证据与排错参考，并标注已被界面验证取代，不作为验收路径。
- 这些阶段**不单独验收**，与界面就绪后的阶段**一并按 §4 走界面验收**。用户 2026-10-06 确认：S02 暂不验收，等界面做完与 S03 一起验。
- 一并验收时，界面必须能覆盖被搁置阶段的核心结果（如 S02 的预检计数与记录），否则该阶段不得记为已接受。

## 7. 用户结果与阶段接受

自动化通过后只标“待手动审阅”。用户结果保存 docs/implementation/reviews/manual/<阶段ID>/r01-用户审阅结果.md，或由开发者根据用户明确反馈如实整理，并记录来源/日期。一并验收的多个阶段各自记录结果，注明是同一次界面操作。界面操作中发现的工程缺陷与业务口径分歧分别记录。

没有反馈保持待用户操作；不能默认通过，不能把开发者测试当用户审阅。人工分类分歧与工程缺陷分别记录。

收到问题后在批准范围内修复、复审并更新实际指南；收到明确接受后才更新阶段为“阶段已接受”。下一阶段具体方案另行讨论，已有授权范围无需再次批准。
